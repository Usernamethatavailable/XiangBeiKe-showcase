# 修改课时为什么需要保留整次备课的上下文

老师先准备一小时课程，再说“改成45分钟”，通常希望缩短这堂课，同时保留学生水平和教学内容。若每条消息都被当成独立请求，系统就容易忘掉此前条件，甚至重新追问已经说过的信息。

象备课在一次会话中保存当前课程状态，后续消息只修改老师明确提出的部分。

## 数量需要记住来源

“一小时课程”与“准备9道题”可能暂时得到相同题数，但后续行为不同。

按课时得到的题数，在课时变短后需要重新计算。老师明确指定的题数，则优先保留。只保存一个数字，无法判断它在下一轮是否应该变化。

项目已有的真实模型验证使用了虚构课程需求：先输入“一小时课程，业3学生”，得到9题；连续调整难度、换题后仍保持9题；改为45分钟后变为6题，再提出“多给两道”，变为8题。这些结果用于验证状态变化，不代表对真实课堂讲解用时的测量。

## 换题和加题是不同的动作

“换一批”需要替换本轮内容，并排除当前棋例；“多给两道”需要保留已有内容，再追加两道。如果都处理成重新生成，老师已经选好的内容就会丢失。

历史恢复也需要恢复课程状态，而不只是恢复棋例列表。否则界面看起来回到了旧课件，下一句调整却可能按另一套课时或数量条件执行。

## 什么时候结束这段上下文

保留上下文会让连续调整更自然，也需要明确的边界。象备课在切换学生、切换备课方式或开始新备课时隔离旧状态，避免上一位学生的条件影响下一次选题。

这项设计适用于需要反复修改同一份材料的流程。实现代价是需要区分当前状态、条件来源和具体动作，并验证它们在恢复、追加和切换时的组合行为。
